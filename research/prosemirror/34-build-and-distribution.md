# 34 — Build, Packaging, Distribution

How `prosemirror-*` actually ships, how to consume it from the major
bundlers and SSR frameworks, and the cross-version pitfalls that make
PM distinctive among large JS libraries. All citations to the cloned
sources under `/tmp/pm-source/`.

---

## A. Multi-package architecture

PM is **not** one library; it's a constellation of small npm packages,
each independently versioned and published. The cloned source lists
fifteen of them:

```
prosemirror-collab            prosemirror-inputrules        prosemirror-tables
prosemirror-commands          prosemirror-keymap            prosemirror-test-builder
prosemirror-dropcursor        prosemirror-model             prosemirror-transform
prosemirror-example-setup     prosemirror-schema-basic      prosemirror-view
prosemirror-gapcursor         prosemirror-schema-list
prosemirror-history
```

Each has its own `package.json`, `src/`, `dist/`, README, and version
number. Concrete current versions in the source:

- `prosemirror-model@1.25.4`
- `prosemirror-state@1.4.4`
- `prosemirror-view@1.41.7`
- `prosemirror-history@1.5.0`

There is no `prosemirror` umbrella package on npm — consumers depend on
the individual packages they need.

### A.1 Why this matters

Three direct consequences:

1. **Bundle granularity.** A minimal viewer can install just
   `prosemirror-model` + `prosemirror-view` + `prosemirror-state` +
   `prosemirror-transform` and skip history/collab/tables.
2. **Independent release cadence.** `prosemirror-view` ships fixes far
   more often than `prosemirror-model` (the document model is
   intentionally stable).
3. **Cross-version coupling.** A PM app can end up with two copies of
   `prosemirror-state` if a transitive dependency pins a different
   range — see §I for the `instanceof` failures this causes.

The peer-dependency model (§D) and bundler config (§F) exist
specifically to make sure this doesn't happen by accident.

## B. `package.json` exports map (CJS + ESM dual; ESM-first)

Every modern PM package ships dual CJS+ESM via the `exports` field. The
`prosemirror-model` shape is canonical (`prosemirror-model/package.json`):

```json
{
  "name": "prosemirror-model",
  "version": "1.25.4",
  "type": "module",
  "main": "dist/index.cjs",
  "module": "dist/index.js",
  "types": "dist/index.d.ts",
  "exports": {
    "import": "./dist/index.js",
    "require": "./dist/index.cjs"
  },
  "sideEffects": false
}
```

Notable details:

- **`"type": "module"`** — the package is ESM-first; the CJS build is
  the *fallback* under `require`.
- **`"exports"` is conditional, not subpath-mapped** — `prosemirror-model`
  exposes a single entry. Consumers cannot deep-import like
  `prosemirror-model/src/node`; only the top-level barrel is public.
  This is a deliberate API-surface choice.
- **`"main"` + `"module"` are kept** — for older bundlers that don't
  honour `exports`. Modern Vite/webpack/Rollup/esbuild prefer
  `exports`, but the legacy fields ensure decade-old toolchains still
  work.
- **`"sideEffects": false`** — critical for tree-shaking (§E).

`prosemirror-view` is slightly different because it ships CSS:

```json
{
  "exports": {
    ".":                       { "import": "./dist/index.js", "require": "./dist/index.cjs" },
    "./style/prosemirror.css": "./style/prosemirror.css"
  },
  "sideEffects": ["./style/prosemirror.css"],
  "style": "style/prosemirror.css"
}
```

Two things to notice: a separate CSS subpath
(`prosemirror-view/style/prosemirror.css`), and `sideEffects` is a
*targeted array* — only the CSS file has side effects, the JS does not.
This is exactly what tree-shakers want.

## C. `.d.ts` strategy

PM ships **hand-written `.d.ts`** generated by `@prosemirror/buildhelper`
from the TypeScript source. Every `package.json` declares
`"types": "dist/index.d.ts"` and `"prepare": "pm-buildhelper src/index.ts"`.

The build helper does three things:

1. Bundles the TS source into a single `dist/index.js` (ESM) and
   `dist/index.cjs` (CommonJS).
2. Emits a single rolled-up `dist/index.d.ts` with all public types.
3. Strips internal types marked `@internal`.

Key consequences:

- **Public API surface is exactly what's in `dist/index.d.ts`.** If a
  symbol isn't there, you're using an undocumented internal — expect it
  to break across patch versions.
- **No source maps in published builds** for the .d.ts. Stack traces in
  TS-aware tooling will resolve to `dist/index.js` line numbers, not
  `src/*.ts`. For source-line debugging, install from the GitHub source
  with a `prepare` script, or use [patch-package](#k-patch-package-patterns).
- **No subpath types.** Because `exports` is single-entry, you can't
  `import type { ResolvedPos } from "prosemirror-model/resolvedpos"`.
  All types come through the barrel.

## D. Peer dependencies model

PM packages declare *concrete* dependencies on their direct
prerequisites and rely on package managers to dedupe transitive copies.
Compare the shape of `prosemirror-view` vs `prosemirror-state`:

`prosemirror-view/package.json`:
```json
"dependencies": {
  "prosemirror-model": "^1.20.0",
  "prosemirror-state": "^1.0.0",
  "prosemirror-transform": "^1.1.0"
}
```

`prosemirror-state/package.json`:
```json
"dependencies": {
  "prosemirror-model": "^1.0.0",
  "prosemirror-transform": "^1.0.0",
  "prosemirror-view": "^1.27.0"
}
```

Notably, **PM uses `dependencies`, not `peerDependencies`.** This is a
deliberate departure from the React/Vue/Svelte convention. The reasoning:

- The packages are tightly co-evolved and the version ranges are
  controlled by the same maintainer.
- Caret ranges (`^1.0.0`) on a 1.x line allow npm/pnpm/yarn to dedupe
  to a single physical install in the dependency tree.
- A peer-dependency model would push the burden of installing four
  packages onto every consumer, with no upside.

The result is that **the consumer should install the packages they
*directly* import, and the lockfile resolves a single shared copy of
each via dedupe.** The combination of caret ranges + dedupe is what
keeps `instanceof` working (§I).

There is one edge case: `prosemirror-state` depends on
`prosemirror-view`, but `prosemirror-view` also depends on
`prosemirror-state`. This *is* a circular dependency at the package
level — npm tolerates it, and it works because neither side imports the
other at module-evaluation time (only at type/class-reference time
inside functions).

## E. Tree-shaking

`"sideEffects": false` in every PM JS package
(`prosemirror-model/package.json`, `prosemirror-state/package.json`,
`prosemirror-history/package.json`, etc.) tells bundlers that any
unused export can be dropped. The exception is `prosemirror-view`,
which marks its CSS as the only side-effecting file:

```json
"sideEffects": ["./style/prosemirror.css"]
```

Practical guidance:

- A bundle that imports `EditorState` but not `Plugin` will still
  include `Plugin` because the symbols cross-reference internally —
  the barrel re-exports a tightly coupled module graph. Tree-shaking
  helps most at the *package* boundary (skip `prosemirror-tables`
  entirely if unused) rather than within a package.
- Don't import the whole barrel and pluck a single symbol expecting
  the rest to vanish. Instead, structure your dependency list so you
  *don't depend on* the package if you don't need its features.
- The minimum viable PM editor pulls in **~120KB minified** (model +
  state + view + transform). Each additional package adds 5–30KB.

## F. Bundler considerations

### F.1 Vite (ESM-native)

The happy path. PM's `"type": "module"` + `"exports"` are exactly what
Vite wants:

```ts
// vite.config.ts
import { defineConfig } from "vite";
export default defineConfig({
  // No PM-specific config needed.
});
```

Then in your code:

```ts
import { EditorState } from "prosemirror-state";
import { EditorView } from "prosemirror-view";
import { Schema } from "prosemirror-model";
import "prosemirror-view/style/prosemirror.css"; // side-effecting CSS
```

Vite's `optimizeDeps` pre-bundles PM into a single chunk during dev,
which is fine. In prod, Rollup (Vite's build engine) tree-shakes.

### F.2 webpack

webpack 5 honours `exports` by default. The two settings to verify:

```js
// webpack.config.js
module.exports = {
  resolve: {
    extensions: [".ts", ".tsx", ".js", ".mjs"],
    mainFields: ["module", "main"], // ESM first
    conditionNames: ["import", "module", "default"], // for `exports` map
  },
  experiments: { topLevelAwait: true }, // not strictly required
};
```

Older webpack 4 setups need `mjs`/`module` resolution explicitly, and
will silently pick the CJS build of every PM package — functionally
fine, but ~10–15% larger bundle and worse tree-shaking. Upgrading
beats configuring around it.

### F.3 Rollup

Identical to Vite's prod path because Vite uses Rollup. The
`@rollup/plugin-node-resolve` plugin does the right thing:

```js
import resolve from "@rollup/plugin-node-resolve";
import commonjs from "@rollup/plugin-commonjs";
export default {
  plugins: [
    resolve({ exportConditions: ["import", "default"] }),
    commonjs(),
  ],
};
```

### F.4 esbuild

Single-flag setup; `--bundle --platform=browser` picks ESM:

```sh
esbuild src/main.ts --bundle --format=esm --platform=browser \
  --conditions=import,module,default --outfile=dist/bundle.js
```

esbuild does the right thing with `sideEffects: false` and
`exports`. CSS is *not* bundled by default — pipe `prosemirror.css`
through your own CSS pipeline or use `--loader:.css=text` and inject.

## G. SSR frameworks

PM's `EditorView` constructor hits `document` immediately (it
attaches event listeners, mounts a `MutationObserver`). It cannot run
in Node. Every SSR framework needs one of two patterns:

1. **Don't render PM on the server.** Mount it in a client-only effect.
2. **Lazy import.** Load PM modules only on the client.

### G.1 Next.js (App Router and Pages)

Use a client component + `next/dynamic` with `ssr: false`:

```tsx
// editor/Editor.tsx
"use client";
import { useEffect, useRef } from "react";

export default function Editor() {
  const ref = useRef<HTMLDivElement>(null);
  useEffect(() => {
    let view: any;
    (async () => {
      const { EditorState } = await import("prosemirror-state");
      const { EditorView } = await import("prosemirror-view");
      const { schema } = await import("prosemirror-schema-basic");
      view = new EditorView(ref.current!, { state: EditorState.create({ schema }) });
    })();
    return () => view?.destroy();
  }, []);
  return <div ref={ref} />;
}
```

```tsx
// page.tsx
import dynamic from "next/dynamic";
const Editor = dynamic(() => import("./editor/Editor"), { ssr: false });
export default function Page() { return <Editor />; }
```

The dynamic-with-`ssr: false` wrapping is what guarantees PM isn't
imported during server rendering, even transitively.

### G.2 Nuxt 3

Use `<ClientOnly>` plus a client-side composable:

```vue
<template>
  <ClientOnly>
    <ProseEditor />
  </ClientOnly>
</template>
```

Inside the component, import PM in `onMounted` (Composition API). For
plain `<script setup>`, use `import.meta.client` guards or move imports
into `onMounted`.

### G.3 SvelteKit

Mount in `onMount` (which is no-op on the server):

```svelte
<script lang="ts">
  import { onMount, onDestroy } from "svelte";
  let el: HTMLDivElement;
  let view: any;
  onMount(async () => {
    const { EditorState } = await import("prosemirror-state");
    const { EditorView } = await import("prosemirror-view");
    const { schema } = await import("prosemirror-schema-basic");
    view = new EditorView(el, { state: EditorState.create({ schema }) });
  });
  onDestroy(() => view?.destroy());
</script>
<div bind:this={el}></div>
```

If you want the import to be statically analysable for code-splitting,
keep the `await import(...)` form rather than top-level static imports.

### G.4 Remix

Same idea: dynamic import inside `useEffect`. Remix doesn't have a
built-in `dynamic({ ssr: false })`, so you write the effect by hand
exactly as the Next.js example above.

### G.5 Astro

In `.astro` pages PM components must be marked `client:only="react"`
(or your framework). Astro's `client:load` would still SSR the
component shell first.

```astro
---
import Editor from "../components/Editor.tsx";
---
<Editor client:only="react" />
```

### G.6 Common SSR pitfalls

- Importing `prosemirror-view` in a file that runs on the server (e.g.,
  a shared `schema.ts`). Split: keep schema (model-only) in a shared
  file, keep view setup in a client-only file.
- Calling `EditorView` constructor before `useEffect` / `onMount`.
- Using a NodeView whose constructor reads `window`/`document` — same
  fix, only construct on the client.

## H. Pinning strategy

For app code, **caret ranges (`^1.x`) are correct** for every PM
package. The maintainers honour semver, and dedupe across the
constellation works as long as everyone is on the same major.

The exception: **`prosemirror-collab`**.

### H.1 Collab cross-version compatibility

`prosemirror-collab` exchanges *steps* between peers
([20 §3](./20-history-and-collab.md), `prosemirror-collab/src/`). A
step's JSON shape is owned by `prosemirror-transform`, and the *step
type registry* is loaded by name. If two peers have different
`prosemirror-transform` minor versions, a step type added in the newer
version will throw on the older peer:

```
RangeError: No step type new-attr-step defined
```

**Pinning rule for collab apps:** every peer must run *identical*
`prosemirror-transform` *minor* versions. In practice:

- Use exact versions in your `package.json` for `prosemirror-transform`
  and `prosemirror-model` if your collab app has long-lived clients.
- If you can't pin exactly, pin to the minor (`~1.10.0`, not
  `^1.10.0`) and roll out coordinated updates.
- The schema is part of the wire format too — peers must run the same
  schema or use a backwards-compatible migration.

This is the only place in the PM ecosystem where the standard "caret
is fine" rule fails.

## I. Common bundling pitfalls

### I.1 Duplicate `prosemirror-*` installations

The classic PM bug. Two `prosemirror-state` copies in `node_modules`
mean two distinct `EditorState` classes; an instance from one fails
`instanceof` against the other:

```ts
// thrown from `prosemirror-view`'s `updateState`:
if (!(state instanceof EditorState)) throw new Error("...");
```

How it happens:

- A transitive dep pins a different range that doesn't dedupe.
- pnpm with `node-linker=isolated` (default) creates per-package
  `node_modules` and *can* duplicate if peers aren't declared.
- Yarn PnP installs in non-overlapping zones.
- Two separate bundle entrypoints each get their own copy.

How to detect:

```sh
npm ls prosemirror-state
# or for pnpm:
pnpm why prosemirror-state
```

If you see more than one resolved version, dedupe. Common fixes:

- `npm dedupe` / `pnpm dedupe`.
- Pin `prosemirror-state` (and friends) at the top of your dependency
  tree.
- In a monorepo, hoist via the workspace tools.
- For Vite, `resolve.dedupe: ["prosemirror-model", "prosemirror-state",
  "prosemirror-view", "prosemirror-transform"]`.
- For webpack, `resolve.alias` to a single canonical path.

### I.2 Mixed CJS/ESM imports of the same package

Less common, but webpack 4 with mixed ESM/CJS consumers can produce
two distinct module records for `prosemirror-state` — one from the
ESM build, one from the CJS build. Same `instanceof` symptom.
Fix: standardise on one format throughout your app.

### I.3 Loading the CSS twice

If two parts of your app import `prosemirror-view/style/prosemirror.css`
and your bundler doesn't dedupe CSS imports, you'll get duplicate
rules. Cosmetic only — but worth knowing.

### I.4 Importing internal modules

`import { …something… } from "prosemirror-state/dist/state"` will
break on the next patch release because PM's `exports` map only
publishes `.`. Always import from the package root.

### I.5 NodeView code that runs on the server

Any code path that touches `document` or `window` at module-evaluation
time (top-level) will crash SSR. Always wrap in functions/effects.

## J. Tables, dropcursor, gapcursor — optional add-ons

The "non-core" packages (`prosemirror-tables`, `prosemirror-dropcursor`,
`prosemirror-gapcursor`, `prosemirror-example-setup`) follow the same
distribution model. A few are worth flagging:

- **`prosemirror-tables`** ships its own CSS at
  `prosemirror-tables/style/tables.css`.
- **`prosemirror-example-setup`** is a *teaching* package — it bundles
  schema-basic, history, keymap, inputrules, dropcursor, gapcursor,
  and menu. Don't ship it to production; assemble your own.
- **`prosemirror-test-builder`** is `devDependency`-only.

## K. `patch-package` patterns for forking PM in-place

PM is small enough that a one-line fix is usually preferable to a
fork. The standard pattern:

1. Edit `node_modules/prosemirror-view/dist/index.js` (or the .d.ts).
2. `npx patch-package prosemirror-view` — generates
   `patches/prosemirror-view+1.41.7.patch`.
3. Commit the patch file.
4. Add `"postinstall": "patch-package"` to `package.json`.

Common reasons to patch:

- A bug fix landed in `master` but isn't released yet.
- You need to disable a behaviour (e.g., a specific browser quirk
  workaround) for a controlled environment.
- You want to add an `@internal` API to your public surface.

Things to avoid:

- Patching the `.ts` source — PM ships `dist/`, not `src/`. Patch the
  built artefact.
- Patching across major versions. The .d.ts and the .js are
  co-versioned; a patch from 1.41.7 won't apply to 1.42.x cleanly.
- Patching `prosemirror-transform` if you're in a collab app — see §H.

For larger forks, a workspace-overridden install via pnpm's
`pnpm.overrides` or yarn's `resolutions` field is more sustainable
than patch-package, but starts to look enough like a fork that you
should consider just publishing your own scoped package.

## L. Summary checklist for shipping a PM-based app

- ✅ Use **caret ranges** for every `prosemirror-*` except
  `prosemirror-transform` in collab apps (pin minor).
- ✅ Add **dedupe rules** in your bundler config (Vite
  `resolve.dedupe`, webpack `resolve.alias`).
- ✅ Import CSS from `prosemirror-view/style/prosemirror.css` (and
  `prosemirror-tables/style/tables.css` if used) **once**.
- ✅ For SSR, **dynamically import** PM modules; never construct
  `EditorView` on the server.
- ✅ Mark your editor component `"use client"` (Next.js) /
  `<ClientOnly>` (Nuxt) / `client:only` (Astro).
- ✅ Verify single installations with `npm ls prosemirror-state` etc.
- ✅ Use `patch-package` for one-off fixes; consider scoped forks for
  long-lived divergences.
- ✅ Tree-shake at the **package** boundary: don't install
  `prosemirror-tables` if you don't need it.
- ✅ Watch the **collab pin rule** — every peer on identical
  `prosemirror-transform` minor.

These rules are what take a hand-rolled PM editor from "works on my
machine" to "ships to production across browsers, frameworks, and
collab clients" without the `instanceof` and SSR landmines that
swallow most first-time integrations.
