- [x] Custom block & mark rendering via `BlockDescriptor.toDOM` / `MarkDescriptor.toDOM`. Until now both descriptor fields existed on the public `defineBlock`/`defineMark` API but the editor view ignored them: the block switch in `packages/editor/src/view.ts:updateBlockElement` was hardcoded for the nine built-in types and any unknown `node.type` fell through to a generic paragraph render, while `wrapForMark` was a hardcoded mark-name switch. Wiring required three coordinated changes. (1) The mark contract: descriptor `toDOM` now returns an *empty wrapper* — the editor inserts the span's text (and any nested mark wrappers) inside it. The previous built-in `toDOM` impls in `packages/core/src/builtins.ts` set `el.textContent = p.text`, which would clobber nested marks like bold-inside-link if those impls were ever actually invoked; they're now stripped. `mentionMark.toDOM` additionally stamps `data-atomic="true"` to preserve the atomic-Backspace contract previously enforced by the hardcoded `case 'mention'` branch. - [x] React-component custom blocks via `BlockDescriptor.toComponent`. The view layer is framework-agnostic so it can't import React directly; instead `ViewOptions` gained a `renderReactBlock?: (host, payload, desc) => void` bridge that the editor calls whenever it renders a custom block whose descriptor defines `toComponent` (and not `toDOM`). The view creates a stable host element inside the block's wrapper — `<div data-plim-react-block-id="{id}" contenteditable="false">` — stashed on the wrapper as `el.__plimReactHost` so re-renders reuse the same DOM node and React reconciliation preserves component-local state across transactions. `renderCustomBlock` now branches: `toDOM` → existing DOM-only path; `toComponent && renderReactBlock` → host-element path; falls back to the generic paragraph render if neither fires (e.g., a `toComponent` descriptor mounted in a non-React host). React-component blocks are treated as atomic: caret entry is disabled, the component owns its DOM, and `payload.content` is `[]` (editable React blocks would require the component to render a `[data-block-content]` element the editor can text-map into — explicit follow-up). `DeriveEditorOptions.renderReactBlock` threads the bridge through `deriveEditor` to `mountView`. In `<PlimEditor>`, the bridge maintains a `Map<HTMLElement, ReactRoot>`: `createRoot(host)` once per host, `root.render(desc.toComponent(payload))` on every call. Cleanup discipline: on every transaction the bridge queues a microtask that walks the roots map and unmounts any whose host is no longer `host.isConnected` — by the time the microtask drains, view.update has already run so the connected/disconnected check reflects the post-tx DOM. PlimEditor unmount unmounts all remaining roots in a deferred microtask too (createRoot's `unmount` cannot run inside another React commit). Three new browser tests in `packages/react/test/custom-block.browser.test.tsx`: (a) seeded doc with a `react_callout` block renders the React component inside `[data-plim-react-block-id]` with `contenteditable=false`, attrs forwarded as props, textContent threaded through; (b) `setBlockAttrs` re-renders the component with new props while `useState`-managed component-local state survives across the tx (proves host stability + reconciliation); (c) `removeBlock` triggers the microtask reap and the component's `useEffect` cleanup fires, the host is gone from the DOM, and the React root is unmounted (proves no leaks). `MarkDescriptor.toComponent` is still untouched — marks are inline and per-render which makes a per-mark React root impractical in performance terms; the historical pattern of styling marks via `toDOM` (empty wrapper + inserted content) is sufficient for nearly every use case. If a real consumer needs React-driven marks we can add an inline mount-point pattern (`<span data-plim-react-mark>` + portal pool) as a follow-up. 41/41 browser + 48/48 node tests pass; example notion-clone build (`@plim/example-notion-clone`) still produces 215KB / 66KB gzip with no new warnings.

- [x] Editable React custom blocks via `<ContentSlot>`. The previous `toComponent` path treated React blocks as atomic — `payload.content` was always `[]` and the host wrapper forced `contenteditable=false` over its entire subtree. Editable blocks now follow the same contract as `toDOM` editable blocks: when the block has `text` defined, the view builds (or reuses) a `[data-block-content]` element, runs `renderTextSpans` against it on every transaction, exposes it via `payload.content[0]`, and passes the same element reference back to the component on every render. The component places it via `<ContentSlot el={payload.content[0]} />` (new export from `@plim/react`), a thin `display: contents` `<span>` whose ref-callback `appendChild`s the slot exactly once and no-ops on subsequent renders (idempotent because the editor reuses the same element across renders). The slot itself carries `contenteditable=true`, overriding the host's `false`, so the chrome buttons / non-text UI in the React tree stay inert while the user can type, select, and run the full transaction surface against the slot's text. Implementation details: (a) `packages/editor/src/view.ts` got a new `findBlockContent(blockEl)` helper that tries the existing fast-path direct-child query first (built-ins / `toDOM` blocks unchanged) and falls back to a descendant search that excludes any `[data-block-content]` reachable through a nested `[data-block-id]` (so child-block content never gets mistaken for the parent's slot); the two text-mapping sites (`locateOffsetInDOM`, the selection→path resolver) both route through it. (b) `renderCustomBlock`'s React branch stashes `__plimReactContentEl` alongside the existing `__plimReactHost` on the wrapper so the slot survives the wrapper-children wipe at the top of each render — the host stays attached to the wrapper, the slot stays attached inside the host's React tree, and the same reference flows through `payload.content[0]` on every commit. (c) `<ContentSlot>` lives in `packages/react/src/index.tsx` as a default export. Result: the same `defineBlock({ name, type, toComponent })` API now scales from atomic React blocks (no `text`) all the way to editable callouts/quotes/etc. (with `text`) with no descriptor-level opt-in and no behavior change for existing atomic React blocks. Coverage: `packages/react/test/editable-react-block.browser.test.tsx` (4 tests) — slot mounts inside the component subtree with `contenteditable=true` and the host stays inert, slot text updates in-place across `replaceRange` transactions and the slot DOM node is the same reference (proves stability), DOM-side caret placement inside the slot resolves to the right `(path, offset)` (proves descendant-search text mapping), and component-local `useState` survives slot text mutations (proves React reconciliation isn't disturbed). 48/48 node + 73/73 browser tests pass; example builds at 249.08KB / 75.97KB gzip.
- [x] Custom blocks needed three behavioral fixes after the editable-React-blocks landing exposed regressions in cross-type rendering and Enter handling, plus a missing markdown-out path. (1) **Stale subtree on type change** — `setBlockType('callout' → 'paragraph')` (the path Backspace-on-empty takes) was leaving the old `.plim-callout` chrome attached to the wrapper because `updateBlockElement`'s type-change cleanup only stripped a hardcoded list of built-in selectors (`.plim-bullet`, `.plim-check`, `hr`, etc.); custom DOM trees rooted anywhere else were left in place, and `ensureContentChild` then appended a fresh empty `[data-block-content]` *after* the orphaned chrome, producing a "ghost callout + empty paragraph" render. (3) **Markdown serialization for custom blocks** — added `toMarkdown?: (payload, ctx) => string | string[]` to `BlockDescriptor` and a new `BlockMarkdownContext` type exposing `serializeInline(spans)`, the raw `spans` array (so descriptors can preserve mark fidelity through `serializeInline`), and `depth` for indent decisions. New `contentToMarkdown(doc, { blocks })` exported from `@plim/markdown` (`packages/markdown/src/index.ts`) walks the doc, calls `descriptor.toMarkdown` for registered custom types and falls through to a hardcoded built-in mapping for paragraph/heading/quote/lists/to_do/code/divider/image/toggle. Inline marks serialize via a precedence-ordered `serializeSpan` (link → code → bold → italic → underline → strikethrough; underline emits `<u>` since commonmark has no syntax for it; unknown marks drop quietly). (4) `deriveEditor` (`packages/editor/src/index.ts`) now defers resolution: declare `blocks: BlockDescriptor[] = []` / `marks: MarkDescriptor[] = []` up-front, build the `editor: AgnosticEditor` handle (which captures references to those arrays), then `for (const desc of plim.resolveBlocks(editor)) blocks.push(desc)` and likewise for marks; extensions are processed with the real handle (was `{} as unknown` placeholder) and their contributed blocks/marks are also resolved with the editor. - [x] Image block ergonomics — resize handle, editable caption, Enter exits to paragraph. Notion-style images need three things the previous render did not provide: (a) the caption beneath the image must accept input without polluting the doc text-mapping (image is an atomic block with no `text`), (b) Enter inside the caption must exit to a fresh paragraph below the image rather than splitting the image block, and (c) an inline resize affordance to commit `attrs.width` as a percentage. Approach is an "isolated subtree" pattern in `packages/editor/src/view.ts`: any element marked `data-plim-isolated="true"` is invisible to the editors selection/input pipeline. New helpers `isolatedAncestor(node)` and `selectionInIsolated()` wired into three call sites: `onSelectionChange` early-returns (so the caret moving inside the caption does not dispatch a setSelection tx), `onBeforeInput` early-returns for everything except `insertParagraph` (routes to `handleIsolatedExit`) and `insertLineBreak` (swallowed — captions are single-line in Notion), and `onKeyDown` early-returns so Backspace/arrows/etc. fall through to the browser. `handleIsolatedExit(opts, iso)` walks up to the wrapping `[data-block-id]`, resolves its path via the new `pathForBlockId(children, id)` helper, and `tx.insertBlock(parentPath + idx+1, { id: newId, type:"paragraph", text:[] })` then sets selection into the new paragraph. `renderImage` rewritten to be persistent across renders: the wrap, `<img>`, caption, and resize handle are stashed on the wrapper (`el.__plimImageWrap`/`__plimImageCaption`/etc.) and reused so an in-progress caption edit survives unrelated transactions. The caption is `contenteditable=true data-plim-isolated="true"`, blur compares the new text against the *latest* state via `pathForBlockId(opts.getState().doc.children, node.id)` (not the closed-over `caption` from render time, which goes stale after the next render) and dispatches `setBlockAttrs({ caption })` only when changed. Render-time text sync skips when the caption is the active element so re-renders cannot clobber in-progress edits. Resize handle (`.plim-image-resize`, `data-plim-isolated="true"`) lives on the right edge: pointerdown captures the pointer, drag clamps width to 60px..wrapWidth (px during drag for snappy feedback), and pointerup converts to a percentage and dispatches `setBlockAttrs({ width: "${pct}%" })` so widths reflow responsively. Width attr is stamped on the `<img>` via `img.style.width = attrs.width || ""`. Example styles in `examples/notion-clone/src/styles.css` add `.plim-image-resize` (8px right-edge strip, opacity 0 → 1 on hover, blue-tinted while dragging via `.plim-image-resize-active`). Coverage: 5 new browser tests in `packages/editor/test/view.browser.test.ts` describe `Image block` — (a) caption is `contenteditable=true data-plim-isolated="true"` and typing into it does not preventDefault (browser owns input) nor add `text` to the image block; (b) blur with changed caption commits `attrs.caption`; (c) Enter inside caption inserts a paragraph at index 1 (image stays at 0), no second image is created, and selection moves into the new paragraph; (d) resize handle is rendered with `data-plim-isolated="true"` and `attrs.width: "50%"` is applied as `img.style.width`; (e) caption text survives an unrelated transaction (typing into another block) — same DOM element preserved, in-progress textContent intact. 62/62 node + 81/81 browser tests pass; example builds at 252.29KB / 76.78KB gzip.
- [x] Image block resize handle visuals fixed. Initial implementation had two structural problems: (1) `.plim-image-wrap` was `display: block` (full container width) so the handle (`right: 0`) floated at the far right edge of the editor, completely detached from the image when its width attr was below 100%; (2) `bottom: 32px` was a brittle guess to clear the caption row — a wrapped two-line caption would overlap the handle. Restructured the DOM in `packages/editor/src/view.ts:renderImage` to insert a `.plim-image-frame` wrapper containing only the `<img>` + handle, with the caption as a sibling of the frame inside the wrap. The wrap is now `display: inline-block` with `max-width: 100%` and the width attr is applied to the *wrap* (not the img) so the handle lands on the image edge regardless of the parent container width. Also avoids the circular sizing issue where an inline-block wrap sized by its child img with `width: 50%` would resolve `50%` against itself. Frame uses `position: relative; line-height: 0` (kills inline-img baseline gap) so handle `top: 0; bottom: 0` cleanly bounds the image vertically. Drag pointer math updated to read `parentWidth = wrap.parentElement.getBoundingClientRect().width` (block content area) and mutate `wrap.style.width` live during drag, committing the px→% conversion on pointerup. Visual upgrade in `examples/notion-clone/src/styles.css`: handle is a 14px-wide hit area on the image right edge with a centered `::before` pill (6×42px, max-height 50%, `rgba(15,15,15,0.6)` background, white border, drop shadow) — matches Notions grip affordance; turns blue (`rgba(35,131,226,0.9)`) while dragging via `.plim-image-resize-active`. Test in `view.browser.test.ts` updated to assert the new structure: `wrap.style.width === "50%"`, `img.style.width === ""`, frame exists, handle is inside frame. 81/81 browser tests pass.
- [x] Block selection mode for atomic (no-`text`) blocks. Notion-style: arrow up from a paragraph into an image (or click an image) puts the editor into "block-selected" mode — the wrapper draws a blue outline, the DOM caret is removed, and Backspace/Delete removes the block with the caret landing in the previous (or next) block. Resolves the previous "no way to delete image blocks" gap (the user could already Backspace at start of paragraph-after-image — `joinBackward` falls through to remove an atomic prev — but the path was non-discoverable). Implemented purely in `packages/editor/src/view.ts:mountView` as view-layer state (`selectedBlockId: string | null`); never persisted into the docs `selection` model. (1) `setBlockSelected(id)` toggles `data-plim-block-selected="true"` on the wrapper, drops the DOM range so two selection visuals dont compete, and refocuses root so subsequent keydowns route here even after a click in an isolated caption. (2) `reapplyBlockSelectedAfterRender` runs after every `render()` to re-stamp the attribute (renders may have wiped/recreated the wrapper) and self-clears the flag if the selected id is gone (block was removed). (3) Click-to-select via a new root-level `pointerdown` listener: bails when the target is in an isolated subtree (caption / resize handle), bails when no `[data-block-id]` ancestor; otherwise looks up the block in state and selects only when `block.text === undefined` (atomic). Clicks on text blocks clear any prior selection. Block drag handle clicks are unaffected because their existing `mousedown` handlers `stopPropagation` before our listener sees them. (4) Keyboard: in `onKeyDown`, when `selectedBlockId !== null` we swallow Escape (clear), Backspace/Delete (`deleteSelectedBlock`), ArrowUp/Left (`moveCaretRelativeToSelected("before")`), ArrowDown/Right (`moveCaretRelativeToSelected("after")`). Bare modifiers (Shift/Ctrl/Meta/Alt) dont drop selection so users can compose shortcuts. Any other key clears selection and falls through to normal handling. Arrow nav INTO atomic neighbours from text: ArrowUp at offset 0 of a text block whose previous sibling is atomic selects it; ArrowDown at end-of-block when the next sibling is atomic selects it. Wrapped multi-line paragraphs naturally walk through their own offsets first before the rule fires. (5) `deleteSelectedBlock` removes the block via `tx.removeBlock(path)` and sets caret either at the end of the previous flat block or the start of the next, with the next-path shifted down by one to account for the removal at the parent level. (6) `moveCaretRelativeToSelected(direction)` is "lateral" if the neighbour is also atomic (block-selection moves to it), otherwise it commits a `setSelection` placing the caret at end (going before) or start (going after) of the text neighbour. (7) Outline styling in `examples/notion-clone/src/styles.css`: `[data-block-id][data-plim-block-selected="true"]::after` paints a 2px `rgba(35,131,226,0.55)` border with `inset: -2px 4px` and a subtle inner white shadow so the outline reads against both light and image backgrounds. Coverage: 5 new browser tests in `packages/editor/test/view.browser.test.ts` describe `Image block` — (a) clicking an image dispatches `pointerdown`, sets `data-plim-block-selected="true"` on the wrapper, and clicking a paragraph clears it; (b) Backspace while selected removes the image and lands the caret at the end of the previous paragraph (offset === text length); (c) Escape while selected clears the visual selection without mutating the doc; (d) ArrowUp at offset 0 of paragraph[1] (after the image) selects the image block; (e) ArrowDown while the image is selected places the caret at start of the next paragraph and clears the block selection.
